# One-time publishing setup

Everything here is done once, by hand, before the first release. Release
mechanics after the setup live in [RELEASING.md](../RELEASING.md).

> **The Maven coordinates are permanent.** Once
> `io.github.eugenedibtsev:media3-decoder-ape` is released to Maven Central,
> the group id and artifact id can never be changed, renamed or removed;
> only new versions can be added. Decide on the name before step 1.

## 1. Sonatype Central Portal account and namespace (~20 min, then a wait)

1. Sign in at https://central.sonatype.com with the **GitHub** account
   `eugenedibtsev` (social login makes the next step trivial).
2. Click your username in the top right corner, choose **View Namespaces**,
   then **Add Namespace**, and enter `io.github.eugenedibtsev`. Signing in
   with the GitHub account usually yields `io.github.<username>` already
   verified; steps 3-5 apply only if it shows **Unverified**.
3. The Portal shows a **verification key** (a random string). Create a
   **public** GitHub repository whose name is exactly that key, under the
   same account.
4. Press **Confirm**. Verification usually completes within
   minutes; if it takes hours, contact Central Support.
5. Delete the temporary verification repository; it is only needed during
   validation.
6. Generate a **user token** at https://central.sonatype.com/usertoken:
   press **Generate User Token** and give it a name and expiry. It returns a
   username/password pair. These two values are
   the `CENTRAL_USERNAME` / `CENTRAL_PASSWORD` secrets used later; the token
   is shown once, so store it in a password manager immediately.

## 2. GPG key (~15 min)

The signing identity must match the identity in the POM, so use the same
noreply address.

```shell
gpg --quick-generate-key "Eugene Dibtsev <287062323+eugenedibtsev@users.noreply.github.com>" rsa4096 sign 2y
gpg --list-secret-keys --keyid-format=long
```

Note the long key id (the part after `rsa4096/`). Then publish the public
half, since Central verifies signatures against a public keyserver:

```shell
gpg --keyserver keyserver.ubuntu.com --send-keys <KEY_ID>
```

Also add the public half to the GitHub account (**Settings → SSH and GPG
keys → New GPG key**, paste the output of
`gpg --armor --export <KEY_ID>`), so the signed release tag shows as
**Verified**:

Export the private half for CI (ASCII-armored, single value):

```shell
gpg --armor --export-secret-keys <KEY_ID> > private-key.asc
```

Keep `private-key.asc` out of any repository; delete it once the secret is
stored in GitHub. Back up the key and its passphrase somewhere durable:
losing it means future releases cannot be signed with the same identity.

## 3. GitHub repository (~15 min)

Create `github.com/eugenedibtsev/media3-decoder-ape`, **public**, with no
README/LICENSE/gitignore generated by GitHub (the repository already has
them; auto-generated files would collide with the first push).

Settings worth enabling right away:

* **Settings → Advanced Security → Private vulnerability reporting →
  Enable.** This is what SECURITY.md points to; without it the advisory
  link 404s.
* **Settings → Rules → Rulesets for `main`:** require a pull
  request before merging, require the `CI` status check to pass, and forbid
  force pushes. Do this **after** the first push, so the initial history
  lands unobstructed.
* **Settings → Actions → General:** allow GitHub Actions, and set workflow
  permissions to read-only (nothing in these workflows writes to the repo).
* **About** sidebar: description and topics (`android`, `media3`,
  `exoplayer`, `monkeys-audio`, `ape`, `audio-codec`); this is how the
  project gets found.

## 4. Actions secrets (~5 min)

**Settings → Secrets and variables → Actions → New repository secret.**
The names must match `.github/workflows/publish.yml` exactly:

| Secret name        | Value                                                        |
|--------------------|--------------------------------------------------------------|
| `CENTRAL_USERNAME` | user token username from step 1.6                            |
| `CENTRAL_PASSWORD` | user token password from step 1.6                            |
| `SIGNING_KEY`      | the whole contents of `private-key.asc`, including the BEGIN/END lines |
| `SIGNING_PASSWORD` | the passphrase of that GPG key                               |

## 5. First push (~5 min)

```shell
git remote add origin git@github.com:eugenedibtsev/media3-decoder-ape.git
git push -u origin main
```

The CI workflow runs on that push: it builds all three ABIs, runs unit
tests, `apiCheck` and the instrumentation suite on an emulator. Wait for it
to go green before anything else; this is the first time the workflows
execute anywhere.

Then apply the branch protection from step 3.

## 6. First release (~30 min including the manual gate)

1. Work through the release checklist in [RELEASING.md](../RELEASING.md),
   including the **physical-device corpus gate**, which is blocking.
2. Tag and push: `git tag v1.0.0 && git push origin v1.0.0`.
3. **Actions → Publish to Maven Central → Run workflow.** It uploads a
   signed bundle as a *staged* deployment.
4. In the Central Portal, open the deployment, check the validation results,
   and press **Publish**. Appearance in search can take a few hours; the
   artifact is resolvable well before that.
5. Verify from a scratch project that
   `implementation 'io.github.eugenedibtsev:media3-decoder-ape:1.0.0'`
   resolves from Central and runs (the same check as the pre-release
   consumer run, against the real repository).
