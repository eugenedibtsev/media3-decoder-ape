# The test corpus

Everything the instrumentation suite decodes is **synthetic**: generated by
the scripts in `media3-decoder-ape/tools/` from a source waveform ffmpeg
computes from a fixed expression, then compressed by the Monkey's Audio
encoders and round-trip verified before it is admitted. Nothing in it is a
recording, and nothing in it is unredistributable. It ships inside the
androidTest APK, so running the suite needs no setup at all.

## What ships

`media3-decoder-ape/src/androidTest/assets/ci_corpus/`, about 27 MB:

| | |
|---|---|
| `manifest.csv` | `filename,expected_pcm_md5,expected_blocks,reference_pcm` |
| `broken.txt` | containers that must fail cleanly |
| `ci_ref.pcm` | reference PCM for the 16-second program |
| `gen-*.ape` | the containers |
| `fuzz/fuzz-*.ape` | deterministic header mutations |

Two source programs are used: a **2-second** one for breadth (most matrix
cells) and a **16-second** one for the cells that need more than two frames
of the 294912-block branch, which is what makes frame-crossing decode and
the seek matrix meaningful. Only the 16-second files carry a reference PCM
and therefore take part in the seek tests.

The 2-second files are roughly one frame each. That is enough to prove a
decode is bit-exact, but not to measure anything about frame-level
parallelism: `ApeWorkerPerfTest` only shows real worker scaling on the
16-second file (measured 2.1x at four workers; the 2-second files stay
flat, as they must).

`—` is not a gap: Insane arrived with 3.99, so no earlier encoder can
produce it.

Every cell the format allows is present. The legacy containers come from
the era encoders named in
[`tools/legacy_encoders.csv`](../media3-decoder-ape/tools/legacy_encoders.csv);
the 3.80 encoder is extracted from its Inno Setup installer by
[`tools/carve_inno13.py`](../media3-decoder-ape/tools/carve_inno13.py),
since `innoextract` cannot parse that installer's ISX headers.

### Axes covered on 3.99

Bit depth 8, 16, 24 and 32-bit float. Mono, stereo, 5.1. Sample rates 44.1,
48, 88.2, 96 and 192 kHz. Tags: APEv2 with embedded cover art, ID3v1, both
at once, and a leading ID3v2 prefix that shifts every container offset.

### Not covered

Generations **3.50–3.79** and everything **below 3.41**: no encoder for
them survives, so no synthetic file can be produced and those decoder
branches ship untested. Below 3.41 nothing is archived at all, and the
only archived 3.50/3.51 installers are truncated captures whose payload
was never saved, so this gap is permanent unless a copy surfaces outside
the Internet Archive. See [RELEASING.md](../RELEASING.md).

## Which encoder produced which file

The legacy containers cannot be built by anything in this repository: they
need Windows binaries from 2001-2002 that are not redistributable.
[`tools/legacy_encoders.csv`](../media3-decoder-ape/tools/legacy_encoders.csv)
records, for each of the 44 legacy files: the encoder, the compression
level, which reference program it came from, the SHA-256 of the encoder
binary, and the SHA-256 of the file itself.

Every row is marked `reproduced=yes`, which is a checkable claim rather
than a note: re-running the named binary on a freshly synthesised
reference produces that exact file, byte for byte. To confirm one yourself,
regenerate the reference and compare:

```shell
ffmpeg -y -f lavfi -c:a pcm_s16le -i \
  "aevalsrc=sin(2*PI*(200+400*t)*t)*0.6+(random(0)-0.5)*0.12|cos(2*PI*(320+250*t)*t)*0.6+(random(1)-0.5)*0.12:s=44100:d=2" \
  ref.wav
MAC.exe ref.wav out.ape -c3000     # -c1000/2000/3000/4000 = fast/normal/high/extrahigh
cmp out.ape .../ci_corpus/gen-397-high.ape
```

Use `d=16` for the three rows marked `16s`. For 3.41 and 3.80 the recorded
hash is of the console front end; both are thin shells over a `MAC.dll`
that must sit beside them to run.

## Regenerating

Needs `ffmpeg` on PATH and the official MAC console tool, built from the
SDK that `src/main/jni/download_maclib.sh` fetches. The legacy slice
additionally needs the era encoders, which are not part of this repository.

```shell
python media3-decoder-ape/tools/generate_ci_corpus.py <out_dir> \
    --mac /path/to/mac --encoders-dir /path/to/old_encoders
```

Each container is compressed, decoded back, and its data-chunk MD5 compared
with the source before it enters the manifest: the corpus checks itself, so
a broken encoder cannot silently poison it. Without `--encoders-dir` the
legacy slice is skipped and only the 3.99 matrix is produced.

The fuzz set comes from `generate_fuzz.py`, seeded, so the same mutations
are produced every time.

## Running against a corpus of your own

The suite never reads anything off the device unless told to. If you have
material of your own (your own recordings, or an encoder that cannot be
redistributed), put it in the layout above and name it explicitly:

```shell
python media3-decoder-ape/tools/push_corpus.py <manifest_dir> [search_dir...]
adb shell am instrument -w -e corpusDir /data/local/tmp/ape_corpus \
    io.github.eugenedibtsev.media3.ape.test/androidx.test.runner.AndroidJUnitRunner
```

Which corpus a run used is announced in logcat under the `ApeCorpus` tag,
so results can always be attributed. Material of your own is never part of
a release artifact and never substitutes for the release checklist.
