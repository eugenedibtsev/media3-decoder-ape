# Releasing media3-decoder-ape

First release? The one-time account, key and repository setup is in
[docs/PUBLISHING_SETUP.md](docs/PUBLISHING_SETUP.md).

## The hard gate: the corpus matrix on a physical device

**No release ships on emulator-green alone.** The suite runs the same
synthetic corpus everywhere: it is the only corpus this project has, it
ships inside the androidTest APK, and it is what CI executes. But an
emulator is not an arm64 phone: the NEON kernels, the 16 KB-page loader
path and real scheduling only exist on hardware. Before *every* release the
maintainer runs the full matrix on a physical arm64 device and checks off
every line. A release with an unchecked line does not happen. This is a
blocking gate, not a recommendation.

### What the corpus covers

Every container generation the project claims support for, at every
compression level that generation's encoder offers, plus the format axes
that cut across them:

* **Generations:** 3.41, 3.80, 3.88, 3.89b2, 3.90b2, 3.91b1, 3.92b2,
  3.94b1, 3.95a1, 3.96, 3.97 (legacy layout) and 3.99 (descriptor layout).
* **Levels:** Fast, Normal, High, Extra High on every generation; Insane on
  3.99, which is where it was introduced.
* **Axes on 3.99:** 8/16/24-bit and 32-bit float; mono, stereo and 5.1;
  44.1 through 192 kHz; APEv2 with cover art, ID3v1, both, and a leading
  ID3v2 prefix.
* **Both seek-table layouts** on 16-second multi-frame files with reference
  PCM: bit table (3.41) and byte table (3.90b2, 3.97).
* Deliberately damaged containers, and a deterministic fuzz set.

Everything in it is generated by the scripts under
`media3-decoder-ape/tools/` from an ffmpeg-synthesised source and
round-trip verified against the reference decoder. No recording, and
nothing that cannot be regenerated from this repository plus the encoders,
is part of it.

### What it cannot cover

Container generations **3.50–3.79 and everything below 3.41** are absent:
no encoder for them survives, so no synthetic file can be produced and
those decoder branches ship untested. Below 3.41 nothing is archived at
all, and the only archived 3.50/3.51 installers are truncated captures
whose payload was never saved. Treat this as a standing gap to disclose,
not one to quietly assume away.

### Release checklist (physical arm64 device)

- [ ] **Full corpus decodes bit-exact.** Every manifest row, on the device.
      Confirm the run used the bundled corpus: the `ApeCorpus` logcat line
      says which corpus was resolved, and no `-e corpusDir` was passed.
- [ ] **Version × level matrix is complete** in the manifest that ran:
      every generation above at every level it supports. A file missing
      from the manifest is silently skipped, so a short manifest makes the
      run look green.
- [ ] **Seek matrix** (100 random seeks, sample-exact against reference
      PCM) on the multi-frame files of both seek-table layouts, including
      at least one legacy Extra High file.
- [ ] **Insane spot-check** on the 3.99 Insane file: playback start, seek
      landing accuracy, no ANR-scale stalls.
- [ ] **Fuzz set** runs with no process death.
- [ ] `apiCheck` green, and the API snapshot diff (if any) is intentional
      and reflected in the version number.
- [ ] CHANGELOG.md has a section for the version being released.

Record the device, OS build and the corpus manifest revision alongside the
release notes.

Testing against material of your own (your own recordings, or an encoder
this project cannot redistribute) is supported and encouraged: push it and
pass `-e corpusDir <path>` (see `tools/push_corpus.py`). It is never part
of a release artifact and never a substitute for the checklist above.

## Release steps

1. Verify the hard gate above is fully checked.
2. Bump `version` in `media3-decoder-ape/build.gradle` (remove `-SNAPSHOT`
   if present); update CHANGELOG.md.
3. Commit, tag `v<version>`, push the tag.
4. Run the **publish** workflow (manual `workflow_dispatch` only; it never
   runs automatically). It builds, signs and uploads to the Sonatype Central
   Portal. Credentials and the GPG key come exclusively from repository
   secrets / environment variables.
5. Verify the staged deployment in the Central Portal UI, then release it.
6. After the artifact is public: run the post-publication consumer check,
   a standalone project resolving the published coordinates with R8
   enabled. The in-repo sample sees the whole project and proves nothing
   about the published artifact.
